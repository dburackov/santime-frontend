# Техническое задание: Интернет-магазин (малый-средний бизнес)

## 1. Общее описание проекта

Проект представляет собой веб-платформу интернет-магазина универсального назначения, рассчитанную на каталог из множества товарных категорий с разнородным набором характеристик (одежда, электроника, товары для дома и т.д.).

Ключевое архитектурное требование проекта: **добавление новой товарной категории и её характеристик должно быть административным действием (через панель управления), а не задачей разработки.** Ни бэкенд, ни фронтенд не должны содержать кода, специфичного для конкретной категории товаров (никаких `if category == "ноутбуки"` ни на сервере, ни в компонентах интерфейса).

Проект стартует как MVP, но изначально проектируется с расчётом на рост до полноценного магазина малого-среднего бизнеса без последующей смены модели данных или архитектурного подхода.

### 1.1. Цели проекта

- Быстрый запуск MVP без потери гибкости на будущее.
- Возможность добавлять категории и атрибуты товаров без участия разработчика после сдачи проекта.
- Приемлемая производительность каталога и фильтров при росте до сотен тысяч товаров.
- Минимизация последующей поддержки со стороны разработчика (проект передаётся заказчику и должен работать автономно).

## 2. Общие архитектурные принципы

### 2.1. Модель данных: гибрид "универсальные поля + JSONB"

- Поля, которые есть у **всех** товаров и участвуют в основной бизнес-логике (цена, остаток на складе, вес, активность товара), хранятся как обычные типизированные колонки таблиц.
- Поля, специфичные для конкретных категорий (RAM, цвет, объём, материал и т.д.), хранятся в колонке `attributes` типа `JSONB` на уровне варианта товара.
- Схема характеристик (какие атрибуты существуют, какого типа, к каким категориям относятся, обязательны ли, участвуют ли в фильтрах) хранится в отдельных метатаблицах и управляется через административную панель.

Это решение принято сознательно вместо классической EAV-модели (таблица `attribute_value` с одной строкой на каждое значение атрибута): JSONB даёт сопоставимую гибкость при значительно более простом и быстром чтении данных, меньшем количестве JOIN'ов и более компактном коде на бэкенде.

### 2.2. Полная схема базы данных

Полный SQL-скрипт создания схемы приведён в Приложении A и является неотъемлемой частью настоящего ТЗ. Кратко состав схемы:

| Таблица | Назначение |
|---|---|
| `category` | Дерево категорий товаров |
| `brand` | Бренды |
| `attribute` | Справочник характеристик (имя, slug, тип, единица измерения) |
| `attribute_option` | Список допустимых значений для характеристик типа OPTION |
| `category_attribute` | Связь категории и характеристики: обязательность, участие в фильтрах, участие в вариантах |
| `product` | Товар (карточка) |
| `product_variant` | Вариант товара (конкретная позиция с ценой, остатком и характеристиками в JSONB) |
| `product_image` | Изображения товара/варианта |
| `order`, `order_item` | Заказы |

### 2.3. Ответственность слоёв

| Слой | Отвечает за |
|---|---|
| **БД (Postgres)** | Хранение данных, целостность связей (FK), базовые constraint'ы, индексация |
| **Бэкенд (Spring Boot)** | Валидация значений атрибутов по метаданным, построение динамических запросов фильтрации, бизнес-логика заказов, автоматическое управление индексами |
| **Фронтенд** | Динамический рендеринг карточек товаров и фильтров на основе метаданных атрибутов, без знания о конкретных категориях |

## 3. Фронтенд: принципы работы

### 3.1. "Условно тупой" фронт

Фронтенд не хранит и не хардкодит информацию о категориях и их атрибутах. Вся структура (какие атрибуты показывать, в каком порядке, каким компонентом их рисовать) приходит с бэкенда как данные.

Единственное, что фронтенд хардкодит — это **конечный, небольшой набор UI-компонентов по типу атрибута** (`attribute.type`), поскольку типов всего 4 и они не меняются:

| Тип атрибута (`attribute.type`) | UI-компонент фильтра | UI-компонент в карточке товара |
|---|---|---|
| `STRING` | Текстовый поиск / список значений | Текстовое поле |
| `NUMBER` | Range slider (диапазон от/до) | Числовое поле с единицей измерения |
| `BOOLEAN` | Чекбокс | Переключатель |
| `OPTION` | Список чекбоксов / select с множественным выбором | Select с допустимыми значениями (`attribute_option`) |

Это единственное осознанное исключение из "тупого фронта" — оно оправдано тем, что типов атрибутов конечное множество и они не связаны с конкретными категориями.

### 3.2. Отображение фильтров (пошагово)

1. Пользователь открывает страницу категории. Фронтенд запрашивает у бэкенда список характеристик, помеченных как `is_filter = true` для данной категории (и всех дочерних, если категория — родительская), отсортированных по `sort_order`.
2. Для каждой характеристики бэкенд возвращает: `name`, `slug`, `type`, `unit`, а для типа `OPTION` — список допустимых значений (`attribute_option`), а для `NUMBER` — фактические минимальное и максимальное значения среди товаров категории (для инициализации диапазона слайдера).
3. Фронтенд рендерит панель фильтров, подбирая компонент по `type` из таблицы выше.
4. При изменении фильтра пользователем фронтенд формирует запрос на список товаров, передавая выбранные значения как параметры (например, `?category=5&price_min=1000&price_max=5000&ram=16GB&color=black`).
5. Список товаров и панель фильтров обновляются на основе ответа бэкенда. Опционально: бэкенд может возвращать количество товаров, соответствующих каждому значению фильтра (фасетные счётчики), чтобы фронт отображал "Чёрный (12)" — этоештатно решается агрегирующими запросами на бэке и не требует изменений на фронте при добавлении новых атрибутов.

### 3.3. Карточка и список товаров

Аналогично фильтрам: бэкенд возвращает для категории список характеристик, помеченных для отображения в карточке, вместе со значениями конкретного товара. Фронтенд рендерит их единым циклом (`v-for` / `.map()`) по списку атрибутов, не различая, что это за категория.

## 4. Бэкенд: принципы работы

### 4.1. Технологический стек

- Spring Boot, Spring Data JPA, Hibernate 6 (нативная поддержка JSONB через `@JdbcTypeCode(SqlTypes.JSON)`).
- PostgreSQL как основная СУБД.
- Динамическое построение запросов фильтрации — через QueryDSL (или Criteria API + `cb.function()` для обращения к JSONB, если требуется остаться в чистой JPA-экосистеме без дополнительных зависимостей — выбор фиксируется на этапе технического дизайна реализации).

### 4.2. Валидация атрибутов

Поскольку JSONB не даёт БД-уровневой валидации типов и допустимых значений (в отличие от нормализованной EAV с FK на `attribute_option`), валидация полностью переносится на сервисный слой бэкенда и выполняется при создании/обновлении `product_variant`:

- Проверка, что все атрибуты, помеченные `required = true` для категории товара, присутствуют в JSONB.
- Проверка соответствия типа значения `attribute.type` (например, для `NUMBER` — что значение действительно число).
- Проверка, что значения атрибутов типа `OPTION` входят в список `attribute_option` для данной характеристики.
- Отклонение попытки сохранить атрибут, не привязанный к категории товара через `category_attribute`.

### 4.3. Механизм фильтрации на бэкенде

Фильтрация товаров строится по следующим принципам:

1. **Точное совпадение / принадлежность множеству значений** (тип `STRING`, `OPTION`, `BOOLEAN`) — выполняется через оператор JSONB `@>` (containment), с использованием единого GIN-индекса на всю колонку `attributes`. Индекс создаётся один раз при миграции схемы и не требует обслуживания при добавлении новых атрибутов.

2. **Диапазонная фильтрация** (тип `NUMBER`, например "цена от X до Y", "объём памяти от 8 до 32 ГБ") — выполняется приведением значения из JSONB к числовому типу (`(attributes->>'slug')::numeric`) и сравнением с границами диапазона. Для приемлемой производительности такие запросы используют expression-индекс, созданный под конкретный атрибут (см. п. 4.4).

3. Все фильтры комбинируются через построитель динамических условий (`Specification` / QueryDSL `BooleanBuilder`) на основании списка активных фильтров, переданных с фронта. Набор фильтров не хардкодится — код фильтрации одинаков для любой категории и любого набора характеристик.

4. Универсальные поля (цена, наличие на складе, бренд, категория) фильтруются напрямую по обычным колонкам, без обращения к JSONB — с использованием стандартных B-tree индексов.

### 4.4. Автоматическое управление индексами (ключевой нюанс, снижающий нагрузку на поддержку)

Чтобы после сдачи проекта заказчику не требовалось участие разработчика для добавления индексов под новые фильтруемые характеристики, реализуется следующий механизм:

- При сохранении записи `category_attribute` с флагом `is_filter = true` для характеристики типа `NUMBER`, сервисный слой бэкенда автоматически создаёт expression-индекс под эту характеристику:

  ```sql
  CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_variant_attr_<slug>
      ON product_variant (((attributes->>'<slug>')::numeric));
  ```

- Индекс создаётся асинхронно, после коммита основной транзакции (`@TransactionalEventListener(phase = AFTER_COMMIT)`), с использованием `CREATE INDEX CONCURRENTLY`, чтобы не блокировать таблицу на запись на "живой" базе.
- Для характеристик типа `STRING`/`OPTION`/`BOOLEAN` отдельный индекс не требуется — их полностью покрывает единый GIN-индекс на колонку `attributes`.
- Таким образом, администрирование индексов становится частью бизнес-логики приложения, а не операционной задачей, требующей ручного вмешательства разработчика или мониторинга нагрузки через `pg_stat_statements`.

### 4.5. Снапшот данных в заказах

Таблица `order_item` хранит копию наименования товара (`product_name`) и артикула (`sku`) на момент оформления заказа, независимо от последующих изменений или удаления товара/варианта в каталоге. Это стандартная практика, обеспечивающая корректность истории заказов.

## 5. Нефункциональные требования и допущения на рост проекта

- Ожидаемый масштаб на горизонте 1-2 лет: до нескольких сотен тысяч товарных позиций, десятки-сотни категорий, до 15-20 фильтруемых числовых характеристик одновременно в системе.
- При превышении указанного масштаба (существенный рост трафика, необходимость полнотекстового и многогранного фасетного поиска) предусмотрен путь эволюции: вынесение поиска и фильтрации в отдельный поисковый индекс (Elasticsearch/OpenSearch) поверх той же реляционной модели, без изменения структуры основной БД, поскольку структура `attributes` (JSONB) может быть напрямую сериализована в документ поискового движка.
- Расширение каталога новыми категориями и характеристиками не должно требовать деплоя кода бэкенда или фронтенда — только действия в административной панели.
- Все операции создания индексов на "живой" базе выполняются без блокировки записи (`CONCURRENTLY`).

## 6. Приложение A: SQL-скрипт схемы базы данных

Полный скрипт создания схемы приведён в отдельном файле `schema.sql`, прилагаемом к настоящему ТЗ. Скрипт включает:

- Таблицы категорий, брендов, товаров, вариантов товаров, изображений.
- Метатаблицы характеристик (`attribute`, `attribute_option`, `category_attribute`).
- Таблицы заказов.
- Базовые индексы (включая GIN-индекс на `attributes`).
- Триггеры автообновления `updated_at`.

Примечание: expression-индексы под конкретные числовые характеристики в скрипте намеренно не создаются заранее — они создаются автоматически приложением в момент назначения характеристики фильтруемой (см. п. 4.4).
